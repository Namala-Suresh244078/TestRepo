# C08 – Complete AWS Availability Zone Failure Simulation

Act as a Senior AWS Cloud Architect, EKS/Kubernetes Architect, and Chaos Engineering Specialist.

## Business objective

We need to implement C08 – Complete Availability Zone (AZ) Failure Simulation using AWS Fault Injection Simulator (FIS).

The existing C08 implementation primarily interrupts EKS worker nodes. This is no longer sufficient.

The revised requirement is to simulate an entire Availability Zone becoming unavailable and demonstrate that the platform continues operating using the surviving Availability Zones.

## Current environment

- AWS EKS cluster with EC2 worker nodes.
- Karpenter manages worker-node provisioning through NodePools.
- AWS Aurora PostgreSQL.
- AWS CloudWatch for monitoring.
- Existing AWS FIS YAML/JSON experiment templates.
- Initial implementation and testing must be performed in QA/non-production.
- Infrastructure as Code approach is currently unknown.

Important existing behaviour:
When we disrupt EKS nodes using FIS and target specific tags, Karpenter automatically provisions replacement nodes. We need to ensure that replacement capacity is provisioned exclusively in healthy AZs during the experiment.

## Expected C08 behaviour

Assume the cluster operates across AZ-A, AZ-B and AZ-C.

When AZ-A is selected for disruption:

1. Simulate AZ-A becoming unavailable using a technically supported FIS experiment.
2. Ensure relevant application workloads and infrastructure components in AZ-A are affected.
3. Prevent new workload capacity from being provisioned in AZ-A during the experiment.
4. Karpenter should provision replacement EC2 worker nodes only in AZ-B/AZ-C.
5. Kubernetes should reschedule affected application pods into the surviving AZs.
6. Application traffic should be served through healthy AZs.
7. Core platform services and application dependencies should remain operational.
8. Aurora PostgreSQL should remain accessible, including appropriate database failover/reconnection behaviour where applicable.
9. CloudWatch should provide evidence of the failure, recovery and application availability.
10. After the experiment, restore the environment and verify normal operations.

## Critical technical investigation

Do not assume that terminating worker nodes is equivalent to AZ failure.

Investigate:

- AWS FIS supported AZ disruption scenarios and actions.
- Whether the selected experiment genuinely simulates AZ unavailability or only selected resource failures.
- AWS Application Recovery Controller (ARC) Zonal Shift and its suitability for traffic evacuation.
- Karpenter support for zonal shift and exclusion of an impaired AZ.
- Karpenter NodePool topology constraints and EC2 subnet/AZ selection.
- EKS control-plane availability versus worker-plane availability.
- Core add-ons, system pods, DNS, networking and ingress.
- ALB/NLB and application traffic routing.
- Aurora PostgreSQL multi-AZ architecture and failover behaviour.

Do not assume that ARC Zonal Shift alone makes an AZ unavailable. Distinguish traffic evacuation from actual infrastructure disruption.

## Required deliverables

1. Analyse the existing C08 implementation.
2. Identify gaps between existing behaviour and the new requirement.
3. Propose a technically feasible AZ failure architecture.
4. Explain the FIS actions, targets, stop conditions and recovery sequence.
5. Explain how Karpenter will avoid provisioning in the disrupted AZ.
6. Identify application and platform components that need validation.
7. Provide an implementation plan.
8. Identify changes needed in existing YAML/JSON templates.
9. Provide pre-experiment and post-experiment validation.
10. Define measurable success criteria.

## Mandatory safety rules

- Start in read-only analysis mode.
- Do not modify existing templates or infrastructure.
- Do not execute AWS FIS experiments.
- Do not terminate resources.
- Do not assume cluster names, subnet IDs, AZ IDs, IAM permissions or resource tags.
- Identify missing information explicitly.
- Never claim complete AZ failure if only EC2 worker nodes have been interrupted.
- Obtain approval before implementation or execution.

First return an architecture assessment and gap analysis. Do not start coding until the proposed design has been reviewed.

Act as an AWS Principal Solutions Architect specialising in EKS, Karpenter, AWS FIS, AWS ARC and high availability.

Design the technical architecture for C08 – Complete AZ Failure Simulation.

### Scenario

Our EKS environment runs across multiple Availability Zones.

We want to simulate AZ-A becoming unavailable.

Expected outcome:
- AZ-A workloads become unavailable.
- Traffic moves to AZ-B/AZ-C.
- Karpenter provisions replacement capacity only in healthy AZs.
- Kubernetes reschedules application pods.
- Applications continue operating.
- Aurora PostgreSQL remains accessible.
- No replacement worker nodes are provisioned in AZ-A during the experiment.

### Analyse these areas

**1. AWS FIS**
- Which supported FIS experiment templates/actions can simulate an AZ disruption?
- What resources are actually affected?
- Does the action affect EC2 instances, networking, load balancing or other services?
- What are the limitations?
- Can we demonstrate a complete AZ failure without claiming that AWS has physically shut down an AZ?

**2. AWS ARC**
- Explain Zonal Shift.
- Explain how traffic evacuation works.
- Explain whether it is required for this scenario.
- Explain how it interacts with ALB and EKS workloads.
- Explain how it differs from infrastructure failure simulation.

**3. Karpenter**
- Explain how to prevent provisioning in AZ-A.
- Assess supported Karpenter zonal shift integration for our installed version.
- Explain ENABLE_ZONAL_SHIFT / --enable-zonal-shift only if supported by the installed version.
- Identify IAM permissions and NodePool configuration changes.
- Explain how to verify that replacement EC2 instances are launched exclusively in healthy AZs.

**4. EKS**
- Worker nodes versus managed control plane.
- Core system pods and application pods.
- CoreDNS, CNI, ingress and other critical components.
- Pod topology spread constraints.
- PodDisruptionBudgets.
- Deployment replicas and anti-affinity.
- Multi-AZ capacity requirements.

**5. Aurora PostgreSQL**
- Writer and reader placement.
- Multi-AZ failover.
- Application connection recovery.
- Potential database availability bottlenecks.

**6. Traffic management**
- ALB/NLB behaviour.
- Target group health checks.
- Cross-zone load balancing.
- Traffic routing to healthy AZs.

3. Component impact matrix.
4. Required AWS services and permissions.
5. Required EKS/Karpenter changes.
6. Risks and limitations.
