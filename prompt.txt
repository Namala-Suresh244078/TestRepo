Story Investigation - Data Model and User/Portal Relationship Analysis

Before implementing Story 357272, perform a complete data model analysis.

Goal:
Determine whether setting a user to INACTIVE is logically correct based on how users are associated with portals.

Analyze:

1. Database schema

   * User-related tables
   * Portal-related tables
   * Role-related tables
   * Assignment/mapping tables

2. For each table provide:

   * Table name
   * Primary key
   * Foreign keys
   * Purpose

3. Generate an Entity Relationship analysis showing:

   User
   Portal
   Portal Admin
   Portal User
   Role
   UserRole
   PortalAssignment

   (or equivalent entities discovered)

4. Determine cardinality:

   * Can one user belong to multiple portals?
   * Can one user be Portal Admin for multiple portals?
   * Can one user be Portal User for multiple portals?
   * Can a portal have multiple admins?
   * Can a portal have multiple users?

5. Trace delete APIs:

   External User Delete:

   * Tables read
   * Tables updated
   * Tables deleted

   Internal User Delete:

   * Tables read
   * Tables updated
   * Tables deleted

6. Determine actual business meaning of delete:

   Is delete currently:

   * removing a user entirely?
   * removing a portal assignment?
   * removing a role assignment?
   * removing portal access only?

7. Impact Analysis:

   If User.status = INACTIVE:

   * Which portals lose access?
   * Which roles are affected?
   * Would access be removed from all portals?
   * Would this violate existing data relationships?

8. Story Validation:

   Compare the story requirement against the current data model.

   Explicitly answer:

   "Does setting a user to INACTIVE correctly implement removing a user from a portal?"

   If NO:
   Explain what should actually be updated instead.

Deliverable:

Produce a markdown document named:

DELETE_USER_DATA_MODEL_ANALYSIS.md

Include:

* ER-style relationship diagram (ASCII is fine)
* Table relationship explanations
* Cardinality analysis
* Delete flow analysis
* Recommendation before implementation

Do not generate code.
Do not modify files.
Only analyze and document.


After that, ask one more powerful question

Additionally, search for real examples in the database access layer.

Provide examples showing:

User A -> Portal X
User A -> Portal Y

or evidence that such a relationship is impossible.

Use repository queries, entity mappings, and foreign key relationships as evidence.

Do not speculate.

Only provide conclusions supported by code/schema.
