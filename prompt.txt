# Story Implementation - User Upsert APIs

## Objective

Implement two new APIs:

```http
POST /api/user/internal/upsert
POST /api/user/upsert
```

The goal is to support create-or-update behavior while preventing duplicate users/persons and preserving existing roles and contacts.

---

## Important Constraints

Before making any code changes:

1. Analyze existing implementations of:

   * `/api/user/internal/create`
   * `/api/user/internal/update`
   * `/api/user/create`
   * related UserService methods
   * role assignment logic
   * contact handling logic
   * portal assignment logic
   * permission validation logic

2. Reuse existing project architecture, patterns, services, repositories, DTOs, entities, validators, and security implementations.

3. Do NOT introduce:

   * new frameworks
   * new persistence approaches
   * new libraries
   * new architectural patterns

4. Do NOT assume behavior not explicitly stated below.

5. Preserve backward compatibility of existing APIs.

---

# API Contracts

## Internal Upsert

```http
POST /api/user/internal/upsert
```

Use the same request and response payload structure currently used by:

```http
/api/user/internal/create
```

No new DTOs should be introduced unless absolutely required by existing project patterns.

---

## External Upsert

```http
POST /api/user/upsert
```

Use the same request and response payload structure currently used by:

```http
/api/user/create
```

---

# Internal User Upsert Rules

## User Lookup

Match existing internal user using:

```text
attuid = pam_user.user_name
```

If no matching user exists:

* Execute existing create flow.

If matching user exists:

* Execute update behavior.

---

## Roles

Existing roles must NOT be removed.

Example:

Current roles:

```text
AGENT
```

Incoming role:

```text
ADMIN
```

Result:

```text
AGENT
ADMIN
```

Role assignment must behave as additive merge logic.

Do not remove roles not present in the request.

---

## Contacts

If incoming contact does not exist:

* Add contact.

If phone number differs:

* Add the new contact.
* Do not delete existing contacts.

Contact handling should follow the same additive behavior as role assignment.

---

## Permissions

Reuse existing permission validation.

Valid permissions include:

```text
INTERNAL_USERS/ADMIN_MANAGEMENT/EDIT
PORTAL_AGENT_ACTIONS/PORTALS/EDIT
PORTAL_ADMIN_ACTIONS/PORTALS/EDIT
```

Do not invent new permission checks.

---

# External User Upsert Rules

## User Matching Logic

Lookup must follow this sequence.

### Step 1

Find active halo identity where:

```text
identityProvider = HALO
externalAccessId matches incoming email
```

Matching must be case-insensitive for externalAccessId.

If found:

* Use the associated existing pam_person.

### Step 2

If no result from Step 1:

Find person in:

```text
PENDING_HALO_ATTACH
```

state whose contact email matches incoming email.

If found:

* Use the existing pam_person.
* Create a new pam_user under that person.
* Apply requested role(s), access, and user attributes.

### Step 3

If no person found:

Execute existing create user/person flow.

---

## Multiple Match Handling

Multiple pam_person matches should not normally occur.

If they do:

* Select the most recent pam_person record (latest record).
* Follow existing project conventions if a standard ordering already exists.

---

## Roles

Role assignment must be additive.

Do not remove existing roles.

---

## Person Reuse

When matching person exists:

* Reuse existing pam_person.
* Do not create duplicate pam_person records.
* Do not create duplicate halo identity records.

---

## Portal Assignment

Do NOT automatically create portal assignment solely because a user already exists.

Follow current create flow behavior only.

Do not introduce new portal-assignment behavior beyond what already exists.

---

## Registration Email

No email handling changes are required.

Current implementation does not send registration emails.

Do not introduce any email functionality.

---

# Response Behavior

Use the same response structure and HTTP status behavior as existing create APIs.

For successful create or update:

```http
200 OK
```

No special UPDATED response object is required.
